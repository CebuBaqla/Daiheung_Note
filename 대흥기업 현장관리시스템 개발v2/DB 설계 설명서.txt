# 대흥기업 현장노트 DB V6 — 설계 초안

2026-09-30 기준. 실제 데이터가 없다는 확인에 따라 V5 이관 대신 신규 구조를 설계했다. 기존 파일과 프로토타입은 그대로 둔다.

## 현재 결과물

- `001_schema.sql`: PostgreSQL용 신규 데이터 구조와 무결성 제약. 독립된 `fieldnote_v6` 스키마에 생성한다.
- `002_workflows.sql`: 허가서 공유, 현장공유 게시, 작업종료 제출을 하나의 트랜잭션으로 처리하는 함수와 제출 후 변경 방지.
- `003_export.sql`: 엑셀 6개 항목을 만드는 조회용 뷰. 사진 자체의 엑셀 삽입은 다운로드 기능에서 처리한다.

**아직 서버에 적용하지 않았다. PostgreSQL 실행 검증 전이며, 앱 연결용 권한 정책까지 완성된 배포본은 아니다.** SQL은 파일 순서대로 빈 시험 DB에서 검증할 대상으로 작성했다. V5 SQL과 섞어 실행하지 않는다. 신규 스키마를 사용하므로 기존 public 테이블을 삭제하거나 변경하지 않는다. 재실행 시 기존 테이블이 있으면 실패하도록 하여 덮어쓰기를 방지한다.

## 확정한 업무 구조

1. 직원과 로그인 계정은 분리한다. 계정이 없는 작업자도 예정·실제 명단에 들어갈 수 있다.
2. 출근·휴가는 직원과 한국 날짜 기준으로 하루 한 건 저장한다. 자동로그인은 DB에 비밀번호를 저장하는 기능이 아니라, 추후 로그인 서비스의 세션 유지로 구현한다.
3. 작업허가서 하나에 목표 작업을 여러 개 연결한다. 단위가 다른 작업의 물량은 합산하지 않는다.
4. 예정 작업자와 실제 작업자를 별도로 저장한다. 반장 확인 시간과 확인자도 남긴다.
5. 장비 목록에서 예정·실제 장비와 대수를 각각 저장한다.
6. 실제 자재명·자재 사용량 입력은 없다. 작업 실적마다 `external_material_used`만 저장하며 기본은 false다. 일부라도 회사 자재 외 자재를 썼으면 true다.
7. 현장별 채팅방은 만들지 않는다. 메시지를 하나의 시간순 목록으로 조회하고, 각 메시지에 현장을 연결한다. **화면이 통합이라는 사실만으로 전 직원에게 모든 정보를 공개한다는 뜻은 아니다.** 읽기 권한 범위는 앱 연결 전에 별도로 확정한다.
8. 긴급현장도 현장 이름만으로 임시 등록할 수 있다. 작업허가서·주소·도면이 없어도 사진 또는 메모만으로 공유한다.
9. 완료사진은 작업종료 보고 전체에 연결한다. 현 프로토타입에서 사진을 작업 항목별로 지정하지 않으므로 엑셀에서도 같은 보고의 사진 묶음이 각 작업 행에 반복될 수 있다.
10. 엑셀은 작업 항목당 한 줄이다. DB의 나머지 정보도 그대로 보존한다.

## 화면에서 DB로 저장하는 흐름

### 작업허가서 공유

관리자가 허가서와 작업 항목·예정 명단·예정 장비·도면을 임시저장한다. `publish_permit`으로 공유하면 타임라인에 허가서 메시지가 한 건 생성된다. 공유 전에는 현장명·주소를 현재 현장 정보에서 복사한다. 공유된 허가서와 하위 자료는 고정한다. 수정본·취소·재발행 기능은 후속 설계 대상으로, 현재 함수는 공유된 허가서를 수정하지 않는다.

### 현장공유

메시지 초안에 사진·도면과 메모를 연결한 다음 `post_share`로 게시한다. 메모·사진·도면 중 하나라도 있어야 한다. 원본 도면과 표시한 이미지는 별도 파일로 보관하고, 표시본은 원본 파일 ID를 참조할 수 있다.

### 작업종료

공유된 허가서마다 보고 초안을 만들고, 허가서의 모든 목표 작업에 대해 실제 물량을 입력한다. 예정 인원·장비를 실제 입력의 초기값으로 복사하되, 실제 명단은 독립적으로 저장한다. `submit_report`가 아래 조건을 검사하고 보고 제출과 메시지 생성을 함께 처리한다.

- 목표 작업 각각에 실제 물량이 있어야 함. 미작업은 0으로 기록.
- 실제 투입 명단 1명 이상 및 반장 확인 필요.
- 완료 체크 3개와 완료사진 1장 이상 필요.
- 하나라도 목표 미달이면 미완료 사유 필요.
- 허가서와 다른 현장이나 작업 항목이 섞이면 거부.

현재는 허가서당 최종 보고 한 건을 기준으로 한다. 여러 작업반이 같은 허가서를 나누어 보고하거나 수정 이력을 남겨야 한다면 보고 버전/작업반 단위를 추가해야 한다. 임의로 개인별 보고·관리자 결재를 넣지 않았다.

## 엑셀 출력 기준

| 출력 열 | 원천 |
|---|---|
| 날짜 | 허가서 작업일 → 보고 작업일 |
| 현장명 | 공유 시 고정한 현장명 |
| 작업자 명단 | 실제 투입 명단의 이름 사본 |
| 목표 작업량 | 작업명 + 목표 수량 + 단위 |
| 실제 작업량 | 작업명 + 실제 수량 + 단위 |
| 작업 사진 | 보고에 연결한 완료사진 목록 |

`excel_work_log`는 제출된 보고만 반환한다. 명단과 사진을 각각 묶은 뒤 연결하므로 작업자 수 × 사진 수만큼 실적 행이 중복되지 않는다. 사진 열은 파일 ID·저장 경로 등의 JSON 목록이다. 실제 XLSX를 만들 때 이를 썸네일로 삽입하거나 링크로 표시한다. **사진을 엑셀 안에 넣을지 링크로 할지는 아직 결정되지 않았다.**

## 파일과 과거 기록 보존

- 사진 파일 자체는 파일 저장소에, DB에는 고유 경로와 파일 정보를 저장한다. 만료되는 URL은 저장하지 않는다.
- 현장명·주소, 작업자명, 장비명은 기록 시 사본을 남겨 나중에 기본 정보를 수정해도 과거 보고가 바뀌지 않게 한다.
- 공유·제출된 기록은 수정·삭제를 막고, 연결된 파일 정보도 변경·삭제를 막는다. 파일 저장소의 객체 덮어쓰기 방지는 저장소 권한 설정 단계에서 별도로 적용해야 한다.
- 소속·개인별 접근 정책, Supabase Auth 연결, 저장소 정책, 실제 서버에서의 동시성 및 롤백 검증은 다음 단계다. 이 초안을 그대로 앱에 공개하지 않는다.

## 다음 결정

DB 구조를 앱에 연결하기 전, **작업반이 자기 반의 기록만 보는지, 회사 전체 기록을 보는지** 정한다. 통합 타임라인 구조는 두 방식 모두 지원한다. 권한을 정하기 전에는 앱 사용자에게 테이블·함수 권한을 부여하지 않는다.
